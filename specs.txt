1.1. MODEL HYBRYDOWY LOCAL-FIRST (FILOZOFIA I PRZEPŁYW DANYCH)
--------------------------------------------------------------------------------
Architektura opiera się na paradygmacie Local-First:
1. Pliki tekstowe (Markdown) oraz pliki płótna (.canvas.json) są nadrzędnym,
   trwałym źródłem prawdy (Source of Truth). Użytkownik posiada 100% kontroli
   nad swoimi plikami na dysku.
2. Relacyjna baza danych SQLite (wraz z silnikiem FTS5) pełni rolę reaktywnego
   indeksu w pamięci i na dysku (Query & Relationship Acceleration Engine).
   Nawet w przypadku całkowitego usunięcia bazy danych SQLite, może ona zostać
   zrekonstruowana w czasie poniżej kilku sekund na drodze pełnego parsowania
   katalogu roboczego (Cold Reindex).

Przepływ zmian (Write/Read Flow):
- Zmiana w UI (edycja notatki / zmiana na Canvasie) -> Zapis asynchroniczny do pliku .md / .canvas.json.
- File System Watcher / Event Emitter -> Emisja zdarzenia FILE_MUTATED.
- Background Indexer Worker -> Parsowanie AST -> Aktualizacja odpowiednich tabel w bazie SQLite.
- Reaktywne interfejsy (Graf, Wyszukiwarka, Asset Drawer) odbierają sygnał i odświeżają widoki bez blokowania wątku głównego UI.


1.2. PEŁNY SCHEMAT BAZY DANYCH SQLITE (DDL SQL)

przez silnik w tle (plik: .workspace/index.db).

PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;

-- ============================================================================
-- 1. TABELA NOTATEK (NOTES)
-- ============================================================================
CREATE TABLE IF NOT EXISTS notes (
    note_id TEXT PRIMARY KEY,               -- Względna ścieżka np. 'notes/historia/konstytucja.md'
    title TEXT NOT NULL,                    -- Tytuł dokumentu (H1 lub nazwa pliku)
    file_path TEXT NOT NULL UNIQUE,         -- Ścieżka bezwzględna / relatywna
    word_count INTEGER DEFAULT 0,           -- Liczba słów
    char_count INTEGER DEFAULT 0,           -- Liczba znaków
    checksum_hash TEXT NOT NULL,            -- Suma kontrolna SHA-256 do szybkiego wykrywania zmian
    created_at INTEGER NOT NULL,            -- Unix timestamp (ms)
    updated_at INTEGER NOT NULL             -- Unix timestamp (ms)
);

-- ============================================================================
-- 2. TABELA ENCJI WIZUALNYCH (VISUAL ENTITIES - v1.2 & v1.3)
-- ============================================================================
CREATE TABLE IF NOT EXISTS visual_entities (
    entity_id TEXT PRIMARY KEY,             -- Unikalny identyfikator np. '@entity_poniatowski_1732'
    title TEXT NOT NULL,                    -- Tytuł / Imię / Etykieta (np. 'Stanisław August Poniatowski')
    media_asset_id TEXT NOT NULL,           -- Odwołanie do tabeli assets (portret, ikona, diagram)
    linked_note_id TEXT,                    -- Opcjonalne powiązanie z główną notatką (FK -> notes.note_id)
    description_snippet TEXT,               -- Krótki ekstrakt tekstowy (do tooltipa i wyszukiwarki)
    entity_type TEXT DEFAULT 'concept',     -- Typ: 'person', 'event', 'concept', 'formula', 'artwork'
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    FOREIGN KEY (linked_note_id) REFERENCES notes(note_id) ON DELETE SET NULL
);

-- ============================================================================
-- 3. TABELA PŁÓCIEN (CANVASES)
-- ============================================================================
CREATE TABLE IF NOT EXISTS canvases (

    title TEXT NOT NULL,                    -- Nazwa płótna
    file_path TEXT NOT NULL UNIQUE,
    node_count INTEGER DEFAULT 0,
    edge_count INTEGER DEFAULT 0,

-- 4. TABELA RELACJI I KRAWĘDZI GRAFU (RELATIONS & EDGES)

    edge_id TEXT PRIMARY KEY,               -- UUID krawędzi
    source_id TEXT NOT NULL,                -- ID źródła (note_id lub entity_id lub canvas_id)
    source_type TEXT NOT NULL,              -- 'note' | 'visual_entity' | 'canvas' | 'block'
    target_id TEXT NOT NULL,                -- ID celu (note_id lub entity_id lub canvas_id)
    target_type TEXT NOT NULL,              -- 'note' | 'visual_entity' | 'canvas' | 'block'
    relation_label TEXT,                    -- Etykieta relacji np. 'INICJATOR', 'SKUTEK', 'PRZYCZYNA'

    origin_canvas_id TEXT,                  -- Jeśli relacja powstała ze strzałki na Canvasie (FK)
    created_at INTEGER NOT NULL,
    FOREIGN KEY (origin_canvas_id) REFERENCES canvases(canvas_id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_edges_source ON graph_edges(source_id);
CREATE INDEX IF NOT EXISTS idx_edges_target ON graph_edges(target_id);
CREATE INDEX IF NOT EXISTS idx_edges_relation ON graph_edges(relation_label);

    byte_size INTEGER NOT NULL,
    width INTEGER,
    height INTEGER,
    created_at INTEGER NOT NULL

-- ============================================================================
-- 6. TABELA ZADAŃ I TEMATÓW (TOPICS & THINGS TO DO)

    title TEXT NOT NULL,                    -- Treść zadania
    priority TEXT NOT NULL,                 -- 'P1' (wysoki/czerwony), 'P2' (średni/żółty), 'P3' (niski/zielony)

1.5. SILNIK WYSZUKIWANIA PEŁNOTEKSTOWEGO (FTS5) I SYNCHRONIZACJA TRIGGERAMI
--------------------------------------------------------------------------------
Aby wyszukiwanie w terminalu (#links) trwało poniżej 2 milisekund, baza SQLite
wykorzystuje automatyczne triggery synchronizujące treść notatek z indeksem FTS5:

-- Trigger: Dodanie nowej notatki
CREATE TRIGGER IF NOT EXISTS trg_notes_fts_insert AFTER INSERT ON notes
BEGIN
    INSERT INTO global_search_fts (item_id, item_type, title, content, tags)
    VALUES (new.note_id, 'note', new.title, '', '');
END;

-- Trigger: Aktualizacja notatki
CREATE TRIGGER IF NOT EXISTS trg_notes_fts_update AFTER UPDATE ON notes
BEGIN
    UPDATE global_search_fts
    SET title = new.title
    WHERE item_id = new.note_id AND item_type = 'note';
END;

-- Trigger: Usunięcie notatki
CREATE TRIGGER IF NOT EXISTS trg_notes_fts_delete AFTER DELETE ON notes
BEGIN
    DELETE FROM global_search_fts WHERE item_id = old.note_id AND item_type = 'note';
END;

Zapytanie wyszukiwania pełnotekstowego z rankingiem BM25 dla terminala (#links):
SELECT item_id, item_type, title, bm25(global_search_fts) as rank
FROM global_search_fts
WHERE global_search_fts MATCH 'Poniatowski*'
ORDER BY rank
LIMIT 20;

2.1. PRECYZYJNA MASZYNA STANÓW SESJI (FINITE STATE MACHINE - FSM)
--------------------------------------------------------------------------------
Zarządzanie czasem i trybem skupienia opiera się na deterministycznej maszynie
stanów (Session State Machine). Zapobiega to niespójnościom danych, wyciekom
czasu oraz błędnemu naliczaniu statystyk w analityce długoterminowej.

Dostępne stany w systemie:
1. `IDLE`              - Stan spoczynku. Użytkownik przegląda bazę, nie ma aktywnej sesji.
2. `CONFIGURING`       - Otwarty modal KROKU 1 (wybór priorytetów P1/P2/P3 z Topics do Things to do).
3. `ACTIVE_FOCUS`      - Sesja aktywna. Licznik czasu bije, monitorowany jest ruch użytkownika.
4. `AUTO_PAUSED`       - Automatyczne wstrzymanie po przekroczeniu progu bezczynności (np. 300 s).
5. `MANUAL_PAUSED`     - Ręczne wstrzymanie przez użytkownika (np. krótka przerwa toaletowa).
6. `EVALUATION_MODAL`  - Użytkownik kliknął "Zakończ sesję" (#session finish) -> modal KROKU 3.
7. `COMMITTED`         - Dane sesji zwalidowane, zapisane w SQLite, pętla zwrotna wykonana.
8. `TERMINATED_ABORT`  - Sesja anulowana przez użytkownika bez zapisu statystyk.

TABELA PRZEJŚĆ STANÓW (STATE TRANSITION MATRIX):
+--------------------+-------------------------+--------------------+------------------------------------------+
| Stan Bieżący       | Zdarzenie (Trigger)     | Nowy Stan          | Akcja w tle (Side Effect)                |
+--------------------+-------------------------+--------------------+------------------------------------------+
| IDLE               | OPEN_SESSION_SETUP      | CONFIGURING        | Pobierz backlog Topics & Tasks           |
| CONFIGURING        | START_SESSION_CLICKED   | ACTIVE_FOCUS       | Inicjalizuj SessionDeltaBuffer, start HB |
| CONFIGURING        | CANCEL_SETUP            | IDLE               | Wyczyść tymczasowy wybór                 |
| ACTIVE_FOCUS       | HEARTBEAT_TICK          | ACTIVE_FOCUS       | Zwiększ focus_seconds o 1s (gdy aktywny) |
| ACTIVE_FOCUS       | IDLE_TIMEOUT_TRIGGERED  | AUTO_PAUSED        | Odejmij czas bezczynności, wyślij alert  |
| ACTIVE_FOCUS       | USER_PAUSE_CLICKED      | MANUAL_PAUSED      | Zatrzymaj stoper, zarejestruj pauzę      |
| ACTIVE_FOCUS       | FINISH_SESSION_CLICKED  | EVALUATION_MODAL   | Zatrzymaj stoper, zagreguj bufor delty   |
| AUTO_PAUSED        | USER_ACTIVITY_DETECTED  | ACTIVE_FOCUS       | Wznów stoper skupienia, ukryj overlay    |
| MANUAL_PAUSED      | USER_RESUME_CLICKED     | ACTIVE_FOCUS       | Wznów stoper skupienia                   |
| EVALUATION_MODAL   | SUBMIT_EVALUATION       | COMMITTED          | Zapisz do SQLite, przelicz wagi SRS      |
| EVALUATION_MODAL   | CANCEL_MODAL            | ACTIVE_FOCUS       | Wróć do edycji w trwającej sesji         |
| COMMITTED          | POST_CLEANUP_DONE       | IDLE               | Wyzeruj bufor RAM, odśwież UI            |
| ACTIVE_FOCUS       | ABORT_SESSION_CLICKED   | TERMINATED_ABORT   | Odrzuć zmiany z bufora sesji             |
| TERMINATED_ABORT   | RESET_TO_IDLE           | IDLE               | Przywróć stan spoczynku                  |
+--------------------+-------------------------+--------------------+------------------------------------------+

Implementacja w TypeScript (Wzorzec Maszyny Stanów):

```typescript
export type SessionState =

export interface SessionContext {
  sessionId: string | null;
  plannedMinutes: number;
  effectiveFocusSeconds: number;
  idleSeconds: number;
  pausesCount: number;

}
```


2.2. ALGORYTM WYKRYWANIA RZECZYWISTEGO SKUPIENIA (HEARTBEAT & ANTI-IDLE)
--------------------------------------------------------------------------------
Aby statystyki sesji nie były zakłamywane przez otwartą aplikację w tle, system
wykorzystuje zaawansowany wielopoziomowy algorytm monitorowania aktywności:

1. Źródła zdarzeń aktywności (Input Event Listeners):
   * `keydown` - wpisywanie tekstu w notatce, wyszukiwanie w terminalu.
   * `pointerdown` / `pointermove` - przesuwanie węzłów, przeciąganie z bocznego panelu.
   * `wheel` - zoomowanie płótna Canvas, przewijanie długiej notatki.
   * `stylus_draw` - rysowanie odręczne rysikiem po Canvasie.

2. Progi czasowe (Timeouts & Thresholds):
   * `T_ACTIVE_DEBOUNCE`   = 500 ms (zapobiega spamowaniu pętli głównej).
   * `T_IDLE_WARNING`      = 180 sekund (3 minuty bez żadnej interakcji).
   * `T_AUTO_PAUSE_CUTOFF` = 300 sekund (5 minut bez akcji -> automatyczna pauza).

3. Formuła obliczania efektywnego czasu skupienia:
   Gdy wykryto bezczynność przekraczającą T_AUTO_PAUSE_CUTOFF, z łącznego czasu
   sesji natychmiast odejmowane jest pełne 300 sekund, aby nie nagradzać
   użytkownika czasem, w którym odszedł od biurka:

   T_effective = T_total_wall_clock - T_manual_pauses - T_accumulated_idle - (T_current_idle >= 300 ? T_current_idle : 0)

4. Algorytm pętli Heartbeat Worker (uruchamiany co 1000 ms w tle):
```typescript
function onHeartbeatTick(ctx: SessionContext): void {
  if (ctx.state !== 'ACTIVE_FOCUS') return;

  const now = Date.now();
  const timeSinceLastActivity = (now - ctx.lastActiveTimestamp) / 1000;

  if (timeSinceLastActivity >= 300) {
    // Przejście w Auto-Pause i cofnięcie 5 minut nieaktywności
    ctx.effectiveFocusSeconds = Math.max(0, ctx.effectiveFocusSeconds - 300);
    ctx.idleSeconds += 300;
    transitionState(ctx, 'AUTO_PAUSED');
    emitEvent('SESSION_AUTO_PAUSED', { reason: 'INACTIVITY_TIMEOUT' });
  } else if (timeSinceLastActivity < 5) {
    // Użytkownik aktywny w ciągu ostatnich 5 sekund
    ctx.effectiveFocusSeconds += 1;
  } else {
    // Stan buforowy (np. czytanie tekstu bez klikania)
    ctx.effectiveFocusSeconds += 1;
  }
}
```


2.3. BUFOR DELTY SESYJNEJ (SESSION DELTA BUFFER W RAM)
--------------------------------------------------------------------------------
Podczas trwania sesji wszystkie mutacje danych NIE trafiają bezpośrednio jako
trwałe statystyki historyczne, lecz są rejestrowane w strukturze `SessionDeltaBuffer`
znajdującej się w pamięci RAM.

Struktura bufora:
```typescript
export class SessionDeltaBuffer {
  public readonly createdNodeIds: Set<string> = new Set();
  public readonly modifiedNodeIds: Set<string> = new Set();
  public readonly createdEdgeIds: Set<string> = new Set();
  public readonly deletedEdgeIds: Set<string> = new Set();
  public readonly completedTaskIds: Set<string> = new Set();
  public readonly addedVisualEntityIds: Set<string> = new Set();
  public readonly srsReviewsCompleted: Array<{ cardId: string; rating: number; latencyMs: number }> = [];
  public writtenCharactersDelta: number = 0;

  public registerNodeCreation(nodeId: string): void {
    this.createdNodeIds.add(nodeId);
    emitEvent('GRAPH_NODE_MUTATED', { nodeId, isSessionNew: true });
  }

  public registerEdgeCreation(edgeId: string): void {
    this.createdEdgeIds.add(edgeId);
    emitEvent('GRAPH_EDGE_MUTATED', { edgeId, isSessionNew: true });
  }

  public registerTaskCompletion(taskId: string): void {
    this.completedTaskIds.add(taskId);
    emitEvent('TASK_STATUS_CHANGED', { taskId, status: 'COMPLETED' });
  }

  public getSummaryMetrics() {
    return {
      nodesAdded: this.createdNodeIds.size,
      edgesAdded: this.createdEdgeIds.size,
      tasksDone: this.completedTaskIds.size,
      visualEntitiesAdded: this.addedVisualEntityIds.size,
      reviewsDone: this.srsReviewsCompleted.length,
      netChars: this.writtenCharactersDelta
    };
  }
}
```

Rola bufora w systemie:
1. **Zasilanie zielonej poświaty grafu:** Silnik renderowania grafu sprawdza,
   czy dany `node_id` znajduje się w `createdNodeIds`. Jeśli tak, renderuje
   wokół niego neonową zieloną otoczkę z pulsacją.
2. **Odporność na przerwanie sesji (Abort Resilience):** Jeśli użytkownik
   zamknie sesję bez zapisu, system może wycofać lub oznaczyć te elementy
   jako utworzone poza sesją bez zanieczyszczania historii analityki.
3. **Błyskawiczne generowanie Modalu Podsumowania (Krok 3):** W momencie kliknięcia
   "Zakończ sesję" podsumowanie pojawia się w czasie < 1 ms, ponieważ dane są
   już zagregowane w pamięci.

3.1. STANDARD VISUAL ENTITY (OBRAZ JAKO PEŁNOPRAWNY WĘZEŁ WIEDZY)
--------------------------------------------------------------------------------
Tradycyjne programy PKM traktują obrazy jako pliki statyczne (tzw. "martwe
załączniki"). W architekturze CogniCanvas v1.3 wprowadzono standard **Visual Entity**,
w którym każdy plik graficzny staje się obiektem semantycznym wyposażonym
w unikalny identyfikator UID, metadane, relacje grafowe oraz powiązaną notatkę.

1. Format Identyfikatora Encji (UID Syntax):
   `@entity_<slug_nazwy>_<hash_crc32>`
   Przykład: `@entity_poniatowski_a8f9`

2. Potok Przetwarzania Mediów (Media Ingestion Pipeline):
   a) Użytkownik upuszcza plik graficzny (PNG, JPG, SVG, WebP) na Canvas lub do notatki.
   b) Hashowanie: Silnik oblicza SHA-256 pliku w celu deduplikacji.
   c) Magazyn mediów: Plik oryginalny zapisywany jest w `/assets/images/<hash>.<ext>`.
   d) Generator miniatur: Background Worker generuje w locie miniaturki w formacie WebP:
      - 64x64 px   (do podglądu w grafie oddalonym i autouzupełnianiu w terminalu),
      - 256x256 px (do kart węzłów na Canvasie i bocznego panelu #links).
   e) Rejestracja w bazie: Wpis do tabeli `visual_entities` i `assets` w SQLite.

3. Struktura Obiektu Visual Entity w Pamięci:
```typescript
export interface VisualEntity {
  entityId: string;                 // '@entity_poniatowski_a8f9'
  title: string;                    // 'Stanisław August Poniatowski'
  archetype: 'person' | 'event' | 'concept' | 'artwork' | 'formula' | 'location';
  mediaAsset: {
    originalPath: string;
    thumbPath: string;
    width: number;
    height: number;
    mimeType: string;
  };
  linkedNoteId: string | null;      // 'notes/Historia/Poniatowski.md'
  tags: string[];                   // ['#krol', '#reformy', '#wiek18']
  backlinksCount: number;           // Wyliczana dynamicznie liczba wystąpień
  createdAt: number;
  updatedAt: number;
}
```

4. Zachowanie Interaktywne w UI (Hover / Click Behavior):
   * **Hover (Najechanie myszą):** Wyświetlenie pływającej karty (Smart Hover Card)
     z miniaturą portretu, streszczeniem powiązanej notatki i listą płócien.
   * **Click (Kliknięcie):** Rozwinięcie pełnego edytora powiązanej notatki
     w wysuwanym drawerze bez opuszczania aktywnego płótna Canvas.
   * **Drag-Link (Przeciągnięcie kotwicy):** Wyciągnięcie strzałki ze zdjęcia
     i połączenie z innym obiektem tworzy semantyczną relację w bazie grafu.


3.2. TRANSKLUZJA I CROSS-CANVAS SYNCHRONIZATION (WSPÓŁDZIELENIE OBIEKTÓW)
--------------------------------------------------------------------------------
Zamiast kopiować pliki i powielać dane, system wykorzystuje mechanizm instancjonowania
wielo-płóciennego (Multi-Canvas Transclusion).

1. Model Relacji: Jeden Obiekt Główny -> Wiele Instancji na Płótnach:
   * Istnieje tylko jeden rekord w `visual_entities` dla Poniatowskiego.
   * Każde płótno `.canvas.json` przechowuje jedynie referencję:
     `{ "type": "visual_entity_node", "entity_id": "@entity_poniatowski_a8f9", "x": 580, "y": 100 }`.

2. Globalny Dispatcher Zmian (Synapse Live Sync):
   Gdy użytkownik edytuje notatkę króla, zmienia jego tagi lub aktualizuje portret:
   a) Wątek roboczy wysyła zdarzenie: `EVENT_BUS.emit('ENTITY_MUTATED', { entityId })`.
   b) Wszystkie otwarte w tle widoki Canvas oraz panel boczny subskrybują to zdarzenie.
   c) Węzły na wszystkich płótnach automatycznie odświeżają swój tytuł, miniaturę
      i etykiety w czasie < 16 ms (1 klatka 60 FPS) bez przeładowywania interfejsu.


3.3. REAL-TIME AST MARKDOWN PARSER (EKSTRAKCJA LINKÓW I GRAFU W LOCIE)
--------------------------------------------------------------------------------
Silnik notatek wykorzystuje dedykowany parser oparty na Abstract Syntax Tree (AST),
który w czasie rzeczywistym (z debouncingiem 250 ms) analizuje tekst użytkownika.

Wzorce rozpoznawania (Regex & AST Rules):
1. **Visual Entity Mention:**
   `\[\[(@entity_[a-zA-Z0-9_\-]+)(?:\|([^\]]+))?\]\]`
   Przykład: `[[@entity_poniatowski_a8f9|Król Stanisław]]`
   -> Tworzy krawędź grafową: `(Current_Note) -[:REFERENCES]-> (@entity_poniatowski_a8f9)`

2. **Tradycyjny Link Dwukierunkowy:**
   `\[\[([a-zA-Z0-9_\- /]+)(?:\|([^\]]+))?\]\]`
   Przykład: `[[Konstytucja 3 Maja]]`
   -> Tworzy krawędź grafową: `(Current_Note) -[:LINKS_TO]-> (Target_Note)`

3. **Tagi Semantyczne:**
   `(?<=\s|^)#([a-zA-Z0-9_\-]+)`
   Przykład: `#reformy`
   -> Zapisuje relację w tabeli `item_tags`.

4. **Bloki Testowe Active Recall (#test):**
   `#test\s*\[(.*?)\]\s*\|\s*\[(.*?)\]`
   Przykład: `#test [Kto uchwalił Konstytucję?] | [Sejm Czteroletni]`
   -> Tworzy obiekt `srs_cards` podpięty pod aktualny plik.

Przepływ przetwarzania tekstu:
```
[ Znak wpisany w edytorze ] ──> [ Debounce 250ms ] ──> [ AST Lexer / Tokenizer ]
                                                              │
                                                              ▼
[ Aktualizacja graph_edges w SQLite ] <── [ Graph Diff Engine ] <── [ Ekstrakcja Relacji ]
```


3.4. SILNIK GRAFU WIEDZY (FORCE-DIRECTED PHYSICS & VISUAL RENDERING)
--------------------------------------------------------------------------------
Graf wiedzy renderowany jest przy użyciu akceleracji WebGL / HTML5 Canvas 2D
z wykorzystaniem symulacji fizycznej opartej na siłach (Force-Directed Simulation):

1. Równania Symulacji Fizycznej:
   * **Siła Odpychania Węzłów (Coulomb Repulsion):**
     Zapobiega nakładaniu się pojęć:
     F_rep(u, v) = -k_rep / (||p_u - p_v||^2) * norm(p_u - p_v)
   * **Siła Przyciągania Krawędzi (Hooke Spring Attraction):**
     Utrzymuje powiązane notatki blisko siebie:
     F_spring(u, v) = k_spring * (||p_u - p_v|| - L_rest) * norm(p_v - p_u)
   * **Siła Grawitacji Centralnej (Center Gravity):**
     Ściąga odizolowane klastry w stronę środka ekranu:
     F_center(u) = -k_center * (p_u - p_origin)

2. Renderowanie Wielopoziomowe (Level of Detail - LOD):
   W zależności od poziomu przybliżenia (Zoom Level z):
   * **LOD 1 (z < 0.4 - Daleki widok):**
     Węzły renderowane są jako proste kolorowe punkty. Krawędzie to cienkie linie (#334155).
   * **LOD 2 (0.4 <= z < 1.0 - Średni widok):**
     Węzły zwykłe: kolorowe dyski z etykietami tekstowymi.
     Visual Entities: okrągłe awatary z miniaturką portretu (przycięcie kołowe `clip()`).
   * **LOD 3 (z >= 1.0 - Bliski widok):**
     Pełne karty z miniaturą w wysokiej rozdzielczości, licznikiem backlinków, ikoną
     archetypu (👑 / 📜 / 🏛️) oraz etykietami semantycznymi na strzałkach (np. "INICJATOR").


3.5. SYSTEM ŚWIECĄCYCH WĘZŁÓW (SESSION GLOW EFFECT & SHADERS)
--------------------------------------------------------------------------------
Kluczową innowacją interfejsu jest mechanizm nagrody wizualnej: węzły i połączenia
stworzone podczas trwającej sesji wyróżniają się dynamiczną poświatą.

1. Algorytm Identyfikacji Węzłów Sesyjnych:
   Dla każdego węzła $i$ w grafie:
   `isSessionNew = sessionDeltaBuffer.createdNodeIds.has(node.id)`
   `isSessionModified = sessionDeltaBuffer.modifiedNodeIds.has(node.id)`

2. Matematyczny Model Pulsacji Poświaty (Pulsing Glow Shader):
   Wartość promienia rozmycia $R_{glow}(t)$ oraz przezroczystości $lpha(t)$
   zależy od czasu sesji $t$:

   R_glow(t) = R_base + A_r * sin(2 * PI * f_pulse * t)
   alpha(t)  = alpha_base + A_a * cos(2 * PI * f_pulse * t)

   Gdzie parametry domyślne to:
   - Częstotliwość pulsacji: f_pulse = 1.2 Hz (spokojny rytm oddechu),
   - Kolor nowego węzła: Neonowy Szmaragd (`#10B981` / `rgba(16, 185, 129, alpha)`),
   - Kolor nowej relacji/krawędzi: Neonowy Błękit (`#38BDF8`).

3. Implementacja Renderowania Poświaty (Canvas 2D Context):
```typescript
function renderGlowingNode(ctx: CanvasRenderingContext2D, node: GraphNode, time: number): void {
  const isNew = sessionDelta.createdNodeIds.has(node.id);

  if (isNew) {
    const pulse = Math.sin(time * 0.005) * 0.5 + 0.5; // Zakres 0.0 .. 1.0
    const blurRadius = 12 + pulse * 8;                // 12px .. 20px

    ctx.save();
    ctx.shadowColor = '#10B981';
    ctx.shadowBlur = blurRadius;
    ctx.strokeStyle = '#34D399';
    ctx.lineWidth = 3.0;

    // Rysowanie obrysu świecącego
    ctx.beginPath();
    ctx.arc(node.x, node.y, node.radius + 2, 0, Math.PI * 2);
    ctx.stroke();
    ctx.restore();
  }

  // Renderowanie właściwego węzła (miniatura lub dysk)
  drawNodeContent(ctx, node);
}
```

4. Płynące Cząstki na Nowych Krawędziach (Flowing Edge Particles):
   Na krawędziach utworzonych podczas bieżącej sesji renderowane są małe,
   przesuwające się świetlne punkty (cząstki fotonowe), które poruszają się
   w kierunku od źródła do celu z prędkością 40 px/s, symbolizując aktywny
   przepływ wiedzy w mózgu użytkownika.

5.1. ALGORYTM POWTÓREK W ODSTĘPACH (SPACED REPETITION - ZMODYFIKOWANY MODEL FSRS)
--------------------------------------------------------------------------------
Silnik zapamiętywania w CogniCanvas v1.3 opiera się na nowoczesnym modelu FSRS
(Free Spaced Repetition Scheduler), który przewyższa klasyczny algorytm SM-2
o ponad 30% wyższą retencją wiedzy przy mniejszej liczbie powtórek.

1. Główne Zmienne Stanu Karty Wiedzy (SRS State):
   * **Stability (S) [w dniach]:** Czas, po którym prawdopodobieństwo przypomnienia
     faktu spada do 90%. Im większa stabilność, tym trwalszy ślad pamięciowy.
   * **Difficulty (D) [skala 1.0 .. 10.0]:** Wrodzona trudność pojęcia. Im wyższa,
     tym wolniej rośnie stabilność przy kolejnych powtórkach.
   * **Retrievability (R) [wartość 0.0 .. 1.0]:** Szansa na poprawne odtworzenie
     informacji w chwili $t$ (liczba dni od ostatniej powtórki):

     R(t, S) = (1 + FACTOR * (t / S))^(-w)
     Dla domyślnych parametrów (gdzie R(S, S) = 0.90):
     R(t, S) = (1 + 19 * (t / S))^(-0.5)

2. Oceny Użytkownika (Review Grades - 1 do 4):
   * `1 - Again (Brak wiedzy / Zapomniane)` -> Zresetowanie stabilności, spadek S.
   * `2 - Hard (Trudne)`                   -> Niewielki wzrost S, wzrost D.
   * `3 - Good (Poprawne / W sam raz)`     -> Standardowy optymalny wzrost S.
   * `4 - Easy (Bardzo łatwe)`             -> Gwałtowny skok S, spadek D.

3. Formuły Aktualizacji Parametrów (Przeliczanie po odpowiedzi):
   * Aktualizacja Trudności ($D'$):
     D' = clamp(D + Delta_D(Grade), 1.0, 10.0)
     Delta_D(Grade) = -w_D * (Grade - 3)

   * Aktualizacja Stabilności po udanej powtórce (Grade >= 2):
     S'_success = S * (1 + exp(w_S0) * (11 - D') * S^(-w_S1) * (exp((1 - R) * w_S2) - 1))

   * Aktualizacja Stabilności po nieudanej powtórce (Grade = 1 - Lapse):
     S'_lapse = min(S_min, w_L0 * D'^(-w_L1) * S^w_L2)

4. Obliczanie Nowego Odstępu Powtórki (Next Interval $I$):
   Dla docelowej retencji $r_{target} = 0.90$:
   I = round(S / FACTOR * (r_target^(-1/w) - 1))  [w dniach]

5.3. METRYKI ANALITYCZNE I STATYSTYKI SESJI (DEEP ANALYTICS)
--------------------------------------------------------------------------------
System gromadzi wielowymiarowe wskaźniki efektywności intelektualnej:

1. Wskaźnik Płynności Skupienia (Flow Index - $FI$):
   Mierzy stopień niezakłóconej, ciągłej pracy umysłowej w skali 0.0 .. 1.0:
   FI = (T_continuous_blocks / T_effective_focus) * (1 - (N_pauses / (T_hours + 1)) * 0.15)
   * $FI > 0.85$ -> Stan głębokiego Flow (nagroda: odznaka *Deep Thinker*).
   * $FI < 0.50$ -> Częste rozproszenia (rekomendacja skrócenia bloku do 25 min).

2. Wskaźnik Rozrostu Sieci Wiedzy (Graph Growth Rate - $GGR$):
   Wskaźnik mierzący, jak intensywnie użytkownik integruje nowe fakty:
   GGR = (Delta_Nodes + 1.75 * Delta_Edges + 0.5 * Delta_VisualEntities) / (T_effective_focus_hours)

3. Współczynnik Retencji (Retention Rate):
   Procent poprawnych odpowiedzi w sesjach powtórkowych:
   Retention = (N_good + N_easy) / (N_again + N_hard + N_good + N_easy) * 100%

4. Silnik Ciągłości Nauki (Streak Engine):
   * Dzień zalicza się do serii (Streak + 1), gdy użytkownik zrealizuje co najmniej
     15 minut efektywnego skupienia ($T_{effective} >= 900	ext{ s}$) LUB ukończy min. 10 powtórek SRS.
   * Mechanizm Zamrożenia Serii (*Streak Freeze*): Automatyczna ochrona 1 dnia nieobecności
     raz na 14 dni, zapobiegająca utracie motywacji.

```typescript
export function applySessionFeedbackLoop(
  topicId: string,
  userScore: number,
  lapsesCount: number
): void {
  let newPriority: 'P1' | 'P2' | 'P3';
  let targetIntervalDays: number;

  if (userScore <= 2.5 || lapsesCount >= 2) {
    newPriority = 'P1'; // Czerwony priorytet na jutro
    targetIntervalDays = 1;
  } else if (userScore <= 4.0) {
    newPriority = 'P2'; // Żółty priorytet standardowy
    targetIntervalDays = 4;
  } else {
    newPriority = 'P3'; // Zielony - utrwalone
    targetIntervalDays = 14;
  }

  db.run(`
    UPDATE tasks_todo 
    SET priority = ?, 
        status = 'BACKLOG',
        time_estimate_minutes = CASE WHEN ? = 'P1' THEN 30 ELSE 15 END
    WHERE topic_id = ? AND status != 'COMPLETED'
  `, [newPriority, newPriority, topicId]);
}
```

6.1. ARCHITEKTURA PROCESÓW I WIELOWĄTKOWOŚCI (THREADING & CONCURRENCY MODEL)
--------------------------------------------------------------------------------
Aby zapewnić płynność interfejsu na poziomie 60–120 FPS bez zacięć (Zero Frame Drops),
nawet przy renderingu tysięcy węzłów na Canvasie i ciągłym parsowaniu tekstu,

```
│ • Renderowanie React/Svelte Viewportów  • Obsługa wejścia użytkownika       │
│ • Obsługa Canvas 2D / WebGL View       • Pasek sesyjny, Drawery, Modale     │
└───────┬────────────────────────────┬────────────────────────────┬───────────┘
        │ PostMessage                │ PostMessage                │ SharedBuffer
        ▼                            ▼                            ▼
┌──────────────────┐        ┌───────────────────┐        ┌────────────────────┐
│ GRAPH SIM WORKER │        │ INDEXER & SQLITE  │        │ HEARTBEAT WORKER   │
│ • D3-Force Fizyka│        │ • FTS5 Tokenizer  │        │ • Odporny na tab-  │
│ • Barnes-Hut Tree│        │ • AST Parser      │        │   throttling timer │
│ • Pozycje (X, Y) │        │ • SQLite WAL Sync │        │ • Focus Tracker    │
└──────────────────┘        └───────────────────┘        └────────────────────┘
```

1. **Main UI Thread (Wątek Główny):**
   * Wyłącznie operacje interfejsu, zbieranie zdarzeń z klawiatury i myszy.
   * Renderowanie klatek na Canvasie przy użyciu `requestAnimationFrame`.

2. **Graph Simulation Worker (Wątek Fizyki Grafu):**
   * Prowadzi obliczenia siłowe metodą Barnes-Hut w przestrzeni wielowątkowej.
   * Przekazuje do UI wyłącznie tablicę gotowych współrzędnych Float32Array: `[x1, y1, x2, y2, ...]`.

3. **Indexer & SQLite Worker (Wątek Parsowania i Bazy):**
   * Skanuje pliki Markdown po wykryciu zmian z debouncingiem.
   * Wykonuje zapytania wyszukiwania pełnotekstowego FTS5 dla terminala `#links`
     bez blokowania wpisywania znaków.

4. **Heartbeat & Focus Worker (Niezależny Wątek Czasowy):**
   * Działa w oparciu o `Worker` lub `SharedWorker`, dzięki czemu przeglądarka

6.3. ODPORNOŚĆ NA AWARIE, BEZPIECZEŃSTWO I ZAPIS DANYCH (DATA RESILIENCE)
--------------------------------------------------------------------------------
Utrata danych podczas intensywnej sesji nauki jest niedopuszczalna. System
posiada 4 warstwy ochrony:

1. **Atomowy Zapis Plików (Atomic Write Protocol):**
   Podczas zapisu notatek `.md` oraz płócien `.canvas.json`:
   a) Dane są najpierw zapisywane do pliku tymczasowego `.workspace/temp_<uuid>.tmp`.
   b) Po pomyślnym zrzuceniu bufora na dysk (fsync), wykonywana jest atomowa
      operacja zmiany nazwy (`fs.rename`), co wyklucza uszkodzenie pliku przy nagłym braku zasilania.

2. **System Migawki Sesji w Locie (Crash Recovery Snapshot):**
   Co 10 sekund trwania sesji w stanie `ACTIVE_FOCUS`, cały obiekt `SessionContext`
   oraz `SessionDeltaBuffer` jest zrzucany do pliku `.workspace/session_current.json`.
   W przypadku awarii komputera, przy ponownym uruchomieniu aplikacja wyświetla komunikat:
   > ⚡ *"Wykryto przerwaną sesję nauki (42 minuty skupienia). Czy chcesz ją dokończyć i zapisać statystyki?"*

3. **Dziennik Zdarzeń SQLite (Write-Ahead Logging - WAL):**
   Baza SQLite działa stale w trybie `PRAGMA journal_mode = WAL`. Pozwala to na
   jednoczesny, bezkolizyjny odczyt bazy przez wątek UI oraz zapis relacji przez Indexer Worker.

4. **Wersjonowanie Notatek i Kopia Bezpieczeństwa (Local History Backups):**
   Aplikacja przechowuje w tle lokalną historię zmian (Diff History) dla każdego
   dokumentu z ostatnich 30 dni w katalogu `.workspace/history/`, umożliwiając
   cofnięcie dowolnej pomyłkowej edycji.
